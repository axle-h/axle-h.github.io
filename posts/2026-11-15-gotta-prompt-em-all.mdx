Do you remember "Choose Your Own Adventure" books?
I read them as a child; they're the books where you had to make choices like:

1. Your curiosity gets the better of you and you enter the deep, dark cave: go to page 300
2. A bat flies out of the cave, you are literally shaking in your boots, you turn back the way you came: go to page 320

Well, I turned Pokémon Red into a "Choose Your Own Adventure" to make it easier and cheaper for an LLM to play through.
It should be playing right now at [gb.ax-h.com](https://gb.ax-h.com).

This started before AI coding agents were any good, when I created a fast and accurate Game Boy emulator, [gbc](https://github.com/axle-h/gbc) (now on [crates.io](https://crates.io/crates/gbc)).
I then ported the [pokered](https://github.com/pret/pokered) disassembly of Pokémon Red to Rust in [poke-agent](https://github.com/axle-h/poke-agent) to make it more reliable and faster to work with an agent.
I made sure the port was faithful (but modernised) by using a deterministic agent that could play through the entire game on both versions.
Finally, I hooked in an LLM through the same harness and got a UI running over HTTP.

Over a few weeks, I got some Anthropic LLMs to play through it 2-3 times each to see how the different model tiers perform with a tight harness like this.
I had some fun with this one. Watching the cheaper LLMs blame my broken game, harness or both, instead of admitting they'd tried the same thing 100 times was comedy.

> TLDR; Opus 5.5 played Pokémon Red the best, Sonnet 5.5 was slightly faster on average and Haiku 5.5 was by far the cheapest; it could finish the game for less than a fiver.

## The `gbc` emulator

`gbc` isn't my first Game Boy emulator.
I developed a dynamically recompiling Game Boy emulator in C# back in 2017 that got a brief moment of fame in the .NET community: <PostLink name="emulating-the-gameboy-cpu-on-dot-net" />.
Unlike that attempt though, `gbc` is actually good.

* It implements more of the hardware that I skipped back on .NET: Game Boy Color, Super Game Boy, cycle-accurate sound and timers etc.
* It passes loads more accuracy tests like blargg, `dmg-acid2`, `cgb-acid2` and (27/28 of) mooneye but it does sacrifice some non-game-breaking accuracy for speed
  e.g. the CPU core does not emulate sub-M-cycle timings and it does not emulate the [OAM corruption bug](https://gbdev.io/pandocs/OAM_Corruption_Bug.html).
* It has been tuned to be fast for headless play e.g. supporting turning off the video and sound hardware.

I have distributed it as a library on [crates.io](https://crates.io/crates/gbc). You can add it to your project with:

```bash
cargo add gbc
```

## The first agent

The first version of the agent hooks into this emulator.
It is a reasonably sized state machine that dips into the running game's memory, makes a decision and executes that decision by pressing buttons on the Game Boy controller.
Having the [pokered](https://github.com/pret/pokered) disassembly helped massively here.
I used its memory map to easily tell which byte in the Game Boy memory represented what state, like the party stats or the current map position.

It did work and I did manage to develop an agent that could reliably finish the game.
But since it could only observe side effects of the running game, decisions and actions were out of step with the native game loop and so they were overwhelmingly
likely to be made halfway through one of the game's routines, resulting in weird state artefacts.
This meant the agent had to be extremely defensive and tolerant of state glitches, making it quite slow and careful to act in the game.

## Porting Pokémon Red to Rust

Coding agents got ridiculously good around this stage of the project.
During one or two quiet weeks, I had a load of spare tokens to use up, so I ported the whole game to Rust.
Obviously this was more for fun and exploring the limits of AI capability than for a good reason, but it did get rid of all that defensiveness in the agent and make the game play way faster.

The porting process was interesting because the disassembly that it's based on is so tied to the Game Boy hardware that it made no sense to do it function by function.
If it had been done like that, it would basically have been a Game Boy emulator that can only run one game.
Instead, I used the disassembly as the specification and the emulator as the oracle: the algorithms (damage, the AI, encounters, pacing) are exact,
but the program structure, the memory layout and the hardware are not carried over.
I also fixed some of the original game's famous mechanical bugs (remember MISSINGNO?), with an option in the menu to switch back to the original Gen 1 behaviour.

Having the emulator and the existing agent was a huge help in validating the correctness of the game, as I was able to easily port the agent over and use
scripted runs through the entire game to catch a ton of bugs and differences.

When playing through the native port, the agent is no longer out of step with the game, so the state glitches and resultant overly defensive slow play are both gone.
The agent still plays as a human would, by pressing buttons; it's just much tidier and reliable.

## Agent tooling

The obvious way to build a game-playing agent is to give the model a tool for everything: `get_party`, `get_bag`, `walk_to`, `use_item`, `read_map` etc.
This doesn't scale very well: every new kind of data is a new tool and a big tool list costs tokens on every request.
Also, a Pokémon-playing agent has very distinct types of decisions to make with little crossover: choosing what move to use in a battle is a very different problem to choosing where on the map to move to.
I actually implemented this and found that the different toolsets used between decision types meant that the agent was really bad at using the prompt cache, so it cost more to run than I'd like.

Instead, I took inspiration from coding agents and provided a virtual filesystem with nodes like:

* `map.png`: a picture of the current map.
   The map rendering is based on [this work](https://blog.vjeux.com/2023/project/pokemon-red-blue-map.html),
   but it also includes NPCs, labelled warps, unreachable ground dimmed and a coordinate ruler down the side.
* `screen.png`: a screenshot of the game.
* `party.md`, `bag.md`, `pc.md`: current stats on things like Pokémon, the bag etc.
* `guide/<Chapter>.md`: a game walkthrough, distilled from the earlier scripted runs and from prior art on the internet.
* `routes.md`, `routes/<Map>.md`: the agent maintains a memory of where the player has travelled, and the route from the current map to any other map.
* `plan.md`: a read/write scratch space for the agent to use for long-term planning between compactions.
* `battle-script.rhai`: since Pokémon battles are very mechanical, the agent has the option of scripting battles to save tokens.
* `issues/<Name>.md`: I found that the stronger models were good at finding issues with the harness or the game itself, so I provided a mechanism for reporting them to me.
   Each issue saves the screen, a save state and the conversation, so I can replay it. The cheaper/weaker models love filing these when they're stuck.

This meant I could get away with just four tools, consistent between all decision types:

| Tool            | What it does                                                         |
|-----------------|----------------------------------------------------------------------|
| `choose_action` | pick an action by id from this turn's menu, ends the turn            |
| `read_file`     | read a file from the virtual filesystem                              |
| `write_file`    | write a file                                                         |
| `edit_file`     | replace a string in a file                                           |

I have no evidence for this, but I think models are already good at understanding filesystems and reading & writing files,
so this actually worked really well without much extra system prompt engineering.
It also solved the caching issue, resulting in a 95% average hit rate over the runs.

## Agent turns

Each turn is like a decision in a "Choose Your Own Adventure" book.
The agent works out what type of decision is next and hands the model the situation plus an indexed menu of everything it can do right now.
Here's a simplified example in Oak's lab when choosing a starter Pokémon:

- `OaksLab:Oak1` — talk to Oak 1
- `OaksLab:Rival` — talk to Rival
- `OaksLab:CharmanderPokeBall` — pick up the Charmander Poke Ball
- `OaksLab:SquirtlePokeBall` — pick up the Squirtle Poke Ball
- `OaksLab:BulbasaurPokeBall` — pick up the Bulbasaur Poke Ball
- `OaksLab:4,11:Warp` — take the warp to PalletTown, arriving at (12, 12)

The model responded to this with a `choose_action(OaksLab:SquirtlePokeBall)` tool call with the summary:

> Choosing Squirtle as starter (good vs Brock); rival battle follows.

The model literally just makes decisions, making it much more efficient than a lower-level approach where it presses buttons on the controller.
Walking to a tile, talking to someone, taking a door or picking a battle move is one decision; the harness handles the dialogue, the menus and the pathfinding.

### Battle scripts

Battles are where turns get expensive: a trainer fight could be a dozen round trips to the API for "use the best move".
So the model can write `battle-script.rhai`, a small [Rhai](https://rhai.rs) program that's run in a sandbox for every battle decision.
It can hand any turn back to the model with `battle.ask()`.
Here's the one Sonnet wrote for the Elite Four, where its Blastoise did all the fighting:

```rust
// Elite Four: Shellby fights solo; Full Restore under 35% HP, else best damaging move.
if battle.me.hp_frac < 0.35 {
    for want in ["FullRestore", "SuperPotion"] {
        for item in battle.bag {
            if item.name == want { battle.use_item(item.name); }
        }
    }
}
// Fainted/other mon out with no damaging move: let me decide.
if battle.best_move == () { battle.ask(); }
battle.fight(battle.best_move);
```

The sandbox has no file, process or network access and is capped on operations, time and depth.
Every new script is put through a mini test suite of made-up battles before it's armed, and the model is told how each one went.

If a script ever throws an error in a real battle, it's disarmed for the rest of the run.
The model gets a report after every scripted battle so it knows what the script does on its behalf.

## The runs

I first experimented with [openrouter/free](https://openrouter.ai/openrouter/free), which selects free models at random.
It's really useful when the quality of the model doesn't matter much, and the usage limits are generous.
In fact, if you add $10 of lifetime credits to OpenRouter, you also get 20x the standard daily rate limit for free models: [see here](https://openrouter.ai/docs/faq).

Sonnet is the fastest gym runner by a mile, all eight badges in just over 4 hours on average, more than an hour ahead of Opus.
Haiku is not far behind Opus until the Elite Four.
Then it all goes sideways at the end: the Elite Four is the real test and any shortcuts taken in training become apparent.

Sonnet still got to the Hall of Fame first on average, but I think Opus played the game better.
I never told any of the models to go as fast as possible, and Opus spent its extra time doing more of the game:

| Model  | Pokémon owned | 8th badge to Hall of Fame | Blackouts after 8th badge | Boss battles lost |
|--------|---------------|---------------------------|---------------------------|-------------------|
| Opus   | 28-30         | 0:53-1:12                 | 0-1                       | 0-1               |

| Haiku  | 16-19         | 3:52-8:50                 | 2-16                      | 3-17              |

* Opus is steady and well planned with no major surprises along the way.
  It caught more Pokémon, including Zapdos in both runs, and turned up at the Elite Four with a team that only blacked out once there across both runs.
* Sonnet progresses a bit faster but fails to plan well enough to train a Pokémon team strong enough to beat the Elite Four before it arrives.
  Every Sonnet run leaned on a single level 71-74 Blastoise, no other Pokémon trained up on any Sonnet run.
* Haiku scrapes along, following the guide instructions verbatim at the expense of its speed of progression.
  It is often not optimally prepared for an encounter, and it gets lost or misdirected sometimes.

### Persistence

You pick up a Nugget early on, worth ¥5000 if you sell it.
It turns out I forgot to implement item selling in the harness: the shop menu only had rows for buying.
Opus did not accept this.
In opus-1 it planned to sell its Nuggets 21 times, at every mart from Cerulean to the Indigo Plateau, right before the Elite Four:

> Healing at the Lobby Nurse, which also makes this my respawn point. Next I'll go to the Clerk to sell Nuggets and buy healing items.

To be fair to Opus, it was right.
Both Opus runs filed the same bug report, which is exactly what the `issues/` folder is for:

> At Cerulean and Vermilion marts the clerk's screen shows BUY/SELL/QUIT, but the mart menu only offers buy: rows and leave — no way to sell items (I want to sell a Nugget for money). Expected sell:\<item\> rows.

> Naming Machop CRITCHOP after its string of critical Karate Chops; goes to PC box since party full.

> Caught Snorlax (woke in a grumpy rage); naming it GRUMPY. It goes to PC since party is full.

Sonnet starts off keen opting to name all of it's Pokémon, but it eventually gives up:

The free models have the best ones.

> Name the caught Weedle with a meaningful nickname reflecting its origin in tall grass and the battle context.

### Blaming the game

Haiku is quick to suspect the game.
In haiku-1, the menu said Hydro Pump was "not very effective" against Venusaur:

> I'm puzzled that the menu lists Hydro Pump as "not very effective" against Venusaur, since Water should be super effective against a Grass-type — this suggests the effectiveness data in the report might be buggy or using different typing logic than expected.

Both Haiku runs also filed an issue that the west of Route 4 was unreachable from Cerulean.
It's a one-way ledge, which haiku-1 even guessed, but it filed an issue anyway:

> Possibly a one-way ledge that I crossed going east earlier, which would make the way back impossible without Cut or Surf. Please check whether the west half is reachable from this corridor

The free models were brutal. In free-2, Lance's Dragonite left it with a Gloom that had run out of PP on every damaging move.
It threw 13 balls at the Dragonite, eight of them Ultra Balls, and filed eight issues in about an hour with titles like:

> Issue: Stuck in Lance's Dragonite battle - softlock

> Missing POKEMON switch option in battle menu

There was nothing to switch to: every other Pokémon had fainted.
It actually went on to beat the Dragonite with Struggle!

## Final thoughts

I'll be honest, this project used up a lot of my time, burnt a lot of electricity and wasted a lot of water, for no actual productive outcome.
I did learn a lot though, particularly how efficient filesystem-based agent tooling is and how to optimise for the prompt cache, which in this case was the difference between a ~$34 Opus run and a ~$265 one.
Oh, and I've now got a Rust port of Pokémon Red!

I think the project worked because the agent does most of the hard work.
Pre-computing the deterministic stuff, like routing between maps and calculating move statistics, left the LLM's context
free for what it's actually good at: making reasoned decisions.

My daughters and I have had fun watching the agent play Pokémon; the per-turn narration makes it feel a lot like watching a person play, and the weaker models make some hilariously bad decisions.

Go and watch the current run at [gb.ax-h.com](https://gb.ax-h.com), and if you want to run your own, the whole thing is one container in [poke-agent](https://github.com/axle-h/poke-agent).
Give it a star ⭐ if you like it!
